# 要件定義レビュー（NASA Appendix C 準拠）

要件定義を NASA Systems Engineering Handbook の
[Appendix C: How to Write a Good Requirement — Checklist](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/)
（C.1〜C.4）に照らしてレビューする。

このスキルでいう「要件」は、NASA の **requirement**（shall で書かれ、検証でき、合意されたもの）を指す。
利害関係者が望むこと（要求、needs / wants）を分析し、取捨選択した結果が要件である。
JIS やシステムズエンジニアリングの文献では requirement を「要求」「要求事項」と訳すことがあるが、
このスキルでは「要件」に統一する。入力の文書が「要求」「要求定義」と書いていても同じように扱う。

このスキルは**指摘と書き換え案を示すまで**を行う。元のファイルは書き換えない。
ユーザーが明示的に頼んだ場合だけ、書き換え案をファイルに反映する。

## 参照ファイル

レビューを始める前に、必ず次の 2 つを読む。

- `references/nasa-checklist.md` — C.1〜C.4 の全チェック項目（ID 付き）と判定の目安
- `references/japanese-terms.md` — 日本語の要件文に適用するための対応表と語のリスト（英語の要件文でも、検証できない語・曖昧語の英語リストとしてこのファイルを使う）

出力の例は `examples/` にある（サンプル要件定義と、それをレビューした結果）。

## 手順

### 1. 入力を把握する

- 対象はファイル（Markdown、テキストなど）か、チャットに貼られたテキスト。
- 言語を判定する（日本語 / 英語 / 混在）。混在している場合は要件文ごとに判定する。
- 次の情報があれば読む。なければ「不明」として扱い、推測で補わない。
  - プロジェクトの用語集、テンプレート・スタイル規則
  - 上位要件（親要件、ミッションのニーズ・目標、ConOps）
  - 要件の階層（システム、サブシステムなど）
- 用語集・上位要件などがないと判定できない項目（C3-03、C4-CS-02、C4-TR-02 など）は、「判定不可」とし、何があれば判定できるかを書く。

### 2. 要件文を切り出す

- 要件らしい文（shall / must / will / should、「〜すること」「〜しなければならない」「〜する」「〜が望ましい」など）を一つずつ切り出す。
- ID がある場合はその ID を使う。ない場合は `R-001` のように連番を振り、**ID がないこと自体を C4-TR-03 の指摘として記録する**。
- 根拠（rationale）、前提、注記は要件文とは分けて扱い、対応する要件に紐づける。
- 1 文に複数の要件が入っている場合も、まずはそのまま 1 件として扱い、C4-CL-03 で指摘する。

### 3. 要件ごとにチェックする

`references/nasa-checklist.md` の項目のうち、**単一の要件文で判定できる項目**（チェックリストで「単位: 要件」となっているもの）をすべて当てはめる。

- 判定は「OK」「NG」「判定不可」の 3 つ。
- NG には必ず、該当する語句を引用し、どの項目のどの点に反するかを書く。
- 日本語の要件文は `references/japanese-terms.md` の対応表で C.1 の shall / will / should を読み替える。助動詞・文末表現だけでなく、文脈（それが義務か、事実か、目標か）で判断する。
- 機械的な語の一致だけで NG にしない。例えば「安全」という語があっても、測定できる基準（「IEC 61508 の SIL 2 を満たす」など）と一緒に書かれていれば NG ではない。

### 4. 文書全体をチェックする

チェックリストで「単位: 文書」となっている項目を、文書全体に当てはめる。

- 完全性：C4-CP-02 の分類（機能、性能、インターフェース、環境 …）ごとに、要件があるか・ないかを一覧にする。対象のシステムに関係のない分類は「対象外の可能性」と書き、決めつけない。
- 一貫性：矛盾する要件の組、表記揺れ（同じものを別の名前で呼んでいるもの）を挙げる。
- 追跡性：ID の有無、上位要件への紐づけの有無。
- TBD / TBR：一覧にし、TBR に根拠・解消方法・担当者・期限があるかを確認する。

### 5. 書き換え案を作る

NG がある要件には書き換え案を出す。

- 元の意図を変えない。意図を推測しないと書けない値（許容範囲、数値の目標など）は、勝手に数値を作らず `[TBR: 〇〇を決める]` のように明示する。
- 1 文に複数の要件があれば分割し、`R-003a`、`R-003b` のように ID を分ける。
- 実装（HOW）が書かれていれば、それで達成したい目的（WHAT）に書き換える。「なぜその要件が必要か」を問い、本当の要件を探す。
- 運用の手順や人員・作業の割り当てが書かれていれば、要件から外して ConOps や SOW（作業範囲記述書）に移すよう提案する。
- 元の要件文と同じ言語で書く。

### 6. 出力する

レビューの説明はユーザーとの会話の言語で書き、要件文の引用と書き換え案は元の要件文の言語で書く。

次の形式で出力する。要件が多い場合（目安 30 件超）は、NG がある要件だけを詳しく書き、OK の要件は ID の一覧にまとめる。

```markdown
# 要件定義レビュー結果

## サマリー
- 対象: <ファイル名またはテキストの説明>（要件 N 件、言語: 日本語/英語）
- NG がある要件: N 件 / 全 N 件
- 主な問題: <多い順に 3 つ程度。例: 検証できない語 (5 件)、許容範囲の欠落 (4 件)、1 文に複数の要件 (3 件)>
- 判定できなかった項目と、その判定に必要な情報: <あれば>

## 要件ごとの結果

### R-001: <要件文の引用>
| 項目 | 判定 | 理由 |
|---|---|---|
| C4-VE-03 検証できない語 | NG | 「高速に」は測定できない。応答時間などの数値で表す |
| C2-P-03 許容範囲 | NG | 性能値に上限・下限がない |

**書き換え案**
> <書き換えた要件文>

（NG の項目だけを表に載せる。全項目 OK なら「NG なし」と書く）

## 文書全体の指摘

### 完全性（要件の分類ごとの有無）
| 分類 | 有無 | 備考 |
|---|---|---|

### 一貫性・追跡性
- ...

### TBD / TBR 一覧
| ID | 内容 | 根拠・解消方法・担当・期限 |
|---|---|---|

## 次にやること
- <優先度の高い順に、要件定義を直すために作者がやること>
```

## 注意

- レビューの基準は NASA Appendix C に限る。独自の基準を足す場合は「NASA の基準外の指摘」と明記して分ける。
- 指摘は具体的に書く。「曖昧です」だけで終えず、どの語がなぜ曖昧で、何に置き換えればよいかを書く。
- 判定に迷った場合は NG にせず「要確認」として理由を書き、作者に判断を委ねる。
