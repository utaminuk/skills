# NASA Appendix C チェックリスト（ID 付き）

出典: NASA Systems Engineering Handbook, Appendix C "How to Write a Good Requirement — Checklist"
https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/

- **ID**: レビュー結果で項目を参照するための ID（このスキル独自の採番）
- **単位**: 「要件」は 1 つの要件文で判定する項目、「文書」は文書全体で判定する項目
- 日本語の要件文に当てはめるときは `japanese-terms.md` を併せて使う

---

## C.1 用語の使い分け（Use of Correct Terms）

| ID | 単位 | 項目 | 判定の目安 |
|---|---|---|---|
| C1-01 | 要件 | **Shall** = requirement（要件） | 要件には shall（またはその日本語相当）を使っている。must / is required to などの混在は、文書のスタイル規則で認められていなければ指摘する |
| C1-02 | 要件 | **Will** = facts or declaration of purpose（事実・目的の宣言） | will が要件の意味で使われていない。will で書かれた義務は shall に直す |
| C1-03 | 要件 | **Should** = goal（目標） | should が要件の意味で使われていない。目標なら目標として扱われているか、要件なら shall に直す |

## C.2 記述形式（Editorial Checklist）

### 人員に対する要件（Personnel Requirement）

| ID | 単位 | 項目 | 判定の目安 |
|---|---|---|---|
| C2-PR-01 | 要件 | "responsible party shall perform such and such" の形になっている | 能動態で、誰が（責任者）何をするか（do, perform, provide, weigh など）が書かれている。受動態（「〜が行われること」）は NG |

### 製品に対する要件（Product Requirement）

| ID | 単位 | 項目 | 判定の目安 |
|---|---|---|---|
| C2-P-01 | 要件 | "product ABC shall XYZ" の形になっている | 主語が製品（システム、ソフトウェア、構造体など）で、「shall + 動詞」の後に何をするかが書かれている |
| C2-P-02 | 要件/文書 | 製品とその下位要素を一貫した用語で呼んでいる | 同じものを別の名前で呼んでいない（例: 「本システム」「アプリ」「サービス」の混在） |
| C2-P-03 | 要件 | 性能・品質の値に許容範囲がある | 「〜以下」「〜以上」「±」「3σ RSS」などで範囲が示されている。値だけ、または値がない場合は NG |
| C2-P-04 | 要件 | 実装が書かれていない（Implementation-free） | WHAT（何が必要か）を書き、HOW（どう実現するか）を書いていない。問題を書き、解決策を書かない。「なぜこの要件が必要か」と問うと本当の要件が見つかることがある |
| C2-P-05 | 要件 | 運用の説明が書かれていない | 製品が満たすべき必要事項か、製品を使う活動かを区別する。「オペレーターは〜」で始まる文はほぼ運用の説明で、要件ではない |

例（NASA の例文）:
- "The system shall operate at a power level of…"
- "The software shall acquire data from the…"
- "The structure shall withstand loads of…"
- "The hardware shall have a mass of…"

## C.3 全般的な品質（General Goodness Checklist）

| ID | 単位 | 項目 | 判定の目安 |
|---|---|---|---|
| C3-01 | 要件 | 文法が正しい | |
| C3-02 | 要件 | 誤字・脱字・句読点の誤りがない | |
| C3-03 | 要件/文書 | プロジェクトのテンプレートとスタイル規則に従っている | テンプレート・規則が与えられていなければ「判定不可」 |
| C3-04 | 要件 | 肯定形で書かれている（shall not ではない） | 「〜してはならない」「〜しないこと」は、できるだけ肯定形に書き換えられないか検討する。安全上の禁止事項など、否定形が自然な場合は「要確認」 |
| C3-05 | 要件/文書 | TBD を最小限にしている | TBD より、最善の見積もり値に TBR を付ける方がよい。TBR には根拠、TBR を外すために必要なこと、担当者、期限を書く |
| C3-06 | 要件 | 前提を含む、理解できる根拠（rationale）がある | 前提は妥当か（同意できるか）。前提はベースライン化の前に確認する |
| C3-07 | 文書 | 文書内の適切な場所にある（付録などではない） | |

## C.4 妥当性確認（Requirements Validation Checklist）

### 明確性（Clarity）

| ID | 単位 | 項目 | 判定の目安 |
|---|---|---|---|
| C4-CL-01 | 要件 | 明確で曖昧さがない | 誤解の余地がない。指示代名詞（this, these /「これ」「それら」）や曖昧語（"as appropriate", "etc.", "and/or", "but not limited to" など）がない |
| C4-CL-02 | 要件 | 簡潔で単純 | |
| C4-CL-03 | 要件 | 1 文に 1 つの考えだけを書いている | 複数の要件を 1 文にまとめていない。要件と根拠を混ぜた段落になっていない |
| C4-CL-04 | 要件 | 主語が 1 つ、述語が 1 つ | 「AとBは〜し、〜する」のような複数の主語・述語は分割する |

### 完全性（Completeness）

| ID | 単位 | 項目 | 判定の目安 |
|---|---|---|---|
| C4-CP-01 | 文書 | できる限り完全に書かれている | 未完成の要件は TBD / TBR として記録され、その一覧が要件と一緒に管理されている |
| C4-CP-02 | 文書 | 要件の漏れがない | 次の分類ごとに要件があるかを確認する: 機能 / 性能 / インターフェース / 環境（開発、製造、試験、輸送、保管、運用） / 施設（製造、試験、保管、運用） / 輸送（製造、組立、引き渡し場所、保管施設内、積載） / 訓練 / 人員 / 運用性 / 安全 / セキュリティ / 外観・物理的特性 / 設計 |
| C4-CP-03 | 文書 | 前提がすべて明示されている | |

### 準拠性（Compliance）

| ID | 単位 | 項目 | 判定の目安 |
|---|---|---|---|
| C4-CM-01 | 要件 | 正しい階層（システム、セグメント、エレメント、サブシステムなど）の要件になっている | 階層の情報がなければ「判定不可」 |
| C4-CM-02 | 要件 | 実装の詳細が書かれていない | C2-P-04 と同じ観点 |
| C4-CM-03 | 要件 | 運用の説明が書かれていない | 運用は要件に混ぜず、ConOps（運用構想）を更新する |
| C4-CM-04 | 要件 | 人員や作業の割り当てが書かれていない | 製品要件に混ぜず、SOW（作業範囲記述書）や作業指示書を更新する |

### 一貫性（Consistency）

| ID | 単位 | 項目 | 判定の目安 |
|---|---|---|---|
| C4-CS-01 | 文書 | 要件同士、また関連システムの要件と矛盾していない | 矛盾する要件の組を挙げる |
| C4-CS-02 | 文書 | 用語がユーザー・発注者の用語、プロジェクトの用語集と一致している | 用語集がなければ「判定不可」とし、用語集の作成を提案する |
| C4-CS-03 | 文書 | 用語が文書全体で一貫して使われ、主要な用語が用語集にある | 表記揺れを挙げる |

### 追跡性（Traceability）

| ID | 単位 | 項目 | 判定の目安 |
|---|---|---|---|
| C4-TR-01 | 要件 | 必要な要件か。親要件を満たすために必要か | 必要な機能や特性か。ニーズとウォンツ（単なる要求）を分ける。必要でなければ要件ではない。「この要件がなかったら最悪どうなるか」と問う |
| C4-TR-02 | 要件/文書 | 上位の要件（またはミッションのニーズ、目標、制約、ConOps）と双方向に追跡できる | 上位要件の情報がなければ「判定不可」 |
| C4-TR-03 | 要件 | 一意に参照できる（一意の番号がある） | 下位の文書から参照できるよう、ID が振られている |

### 正確性（Correctness）

| ID | 単位 | 項目 | 判定の目安 |
|---|---|---|---|
| C4-CR-01 | 要件 | 要件が正しい | 明らかな誤り（単位の誤り、物理的にありえない値など）を指摘する。ドメイン知識が必要な場合は「要確認」 |
| C4-CR-02 | 要件/文書 | 前提が正しい | 前提はベースライン化の前に確認する |
| C4-CR-03 | 要件 | 技術的に実現できる | 明らかに実現できない要件を指摘する。判断できない場合は「要確認」 |

### 機能性（Functionality）

| ID | 単位 | 項目 | 判定の目安 |
|---|---|---|---|
| C4-FN-01 | 文書 | 記述された機能がすべて必要で、全体としてミッション・システムの目標を満たすのに十分 | |

### 性能（Performance）

| ID | 単位 | 項目 | 判定の目安 |
|---|---|---|---|
| C4-PF-01 | 文書 | 必要な性能値とマージンがすべて書かれている | タイミング、スループット、記憶容量、レイテンシ、精度（accuracy と precision）を確認する |
| C4-PF-02 | 要件 | 性能要件が現実的 | |
| C4-PF-03 | 要件 | 許容範囲が厳しすぎない。根拠があり、コストに見合う | 「許容範囲を 2 倍、3 倍にしたら最悪どうなるか」と問う |

### インターフェース（Interfaces）

| ID | 単位 | 項目 | 判定の目安 |
|---|---|---|---|
| C4-IF-01 | 文書 | 外部インターフェースがすべて明確に定義されている | |
| C4-IF-02 | 文書 | 内部インターフェースがすべて明確に定義されている | |
| C4-IF-03 | 文書 | インターフェースがすべて必要かつ十分で、互いに矛盾しない | |

### 保守性（Maintainability）

| ID | 単位 | 項目 | 判定の目安 |
|---|---|---|---|
| C4-MT-01 | 文書 | 保守性の要件が、測定・検証できる形で書かれている | |
| C4-MT-02 | 文書 | 変更の波及が最小になるように書かれている | 要件同士の結合ができるだけ弱い |

### 信頼性（Reliability）

| ID | 単位 | 項目 | 判定の目安 |
|---|---|---|---|
| C4-RL-01 | 文書 | 明確で、測定・検証できる信頼性の要件がある | |
| C4-RL-02 | 文書 | エラーの検出、報告、処理、復旧の要件がある | |
| C4-RL-03 | 文書 | 望ましくない事象（シングルイベントアップセット、データの消失・破損、操作ミスなど）を考慮し、必要な対応が定められている | |
| C4-RL-04 | 文書 | 機能の実行順序についての前提が書かれている。その順序は必要か | |
| C4-RL-05 | 文書 | ソフトウェア・ハードウェアの障害後の生存性を、ハードウェア、ソフトウェア、運用、人員、手順の観点で扱っている | |

### 検証可能性（Verifiability/Testability）

| ID | 単位 | 項目 | 判定の目安 |
|---|---|---|---|
| C4-VE-01 | 要件 | 試験・実証・検査・解析のいずれかで、要件を満たすことを示せる | 要件が書かれた階層（システムレベルなど）で検証できるか。満たしているかを測る方法があるか。検証の基準を書けるか |
| C4-VE-02 | 要件 | 試験の合格基準を決められるほど正確に書かれている | |
| C4-VE-03 | 要件 | 検証できない語を使っていない | `japanese-terms.md` の「検証できない語」を使う |

### データの扱い（Data Usage）

| ID | 単位 | 項目 | 判定の目安 |
|---|---|---|---|
| C4-DU-01 | 要件 | 「don't care」の条件が本当に結果に影響しない | 条件やフラグの値が問題にならない場合（don't care）が明示されているか。正しく特定すると設計の移植性が高まることがある |
